# ADR-002: Database Choice – PostgreSQL + Redis over NoSQL

**Status:** Accepted  
**Date:** 2026-05-18  
**Deciders:** Emmanuel Adoum, Chidima Praise

---

## Context

We need:
- ACID compliance for alert history and user preferences.
- Fast retrieval of recent articles (real‑time feed).
- JSON support for ML outputs (risk scores, forecast bands).
- Scalability to 500+ articles/day.

Options: PostgreSQL, MySQL, MongoDB, Cassandra.

---

## Decision

Use **PostgreSQL 15** as primary relational database and **Redis** as in‑memory cache and task broker.

---

## Rationale

- **PostgreSQL:**
  - ACID guarantees for critical data (alerts, users).
  - `JSONB` column type for flexible risk score schemas.
  - `pgvector` extension for future similarity search on articles.
  - Strong ecosystem (SQLAlchemy, Alembic migrations).
  - Multi‑AZ RDS support.

- **Redis:**
  - Sub‑millisecond latency for live feed caching.
  - Celery task broker (RPC pattern).
  - Deduplication (store article hashes with TTL).
  - Pub/Sub for WebSocket message distribution.

---

## Consequences

- **Positive:** Best of both worlds – strong consistency + high speed caching.
- **Negative:** Two databases increase operational complexity.  
  Redis persistence (RDB/AOF) must be configured for durability.

---

## Alternatives Considered

- **MongoDB** – No ACID for alert acknowledgements, less mature JSON indexing.
- **Cassandra** – Over‑engineered for our scale, eventual consistency not acceptable for user alert history.
- **MySQL** – Good but lacks native JSONB and pgvector‑like extensions.

---

## Compliance

-  Real‑time feed latency (<15 min) – Redis cache.
-  Alert history integrity – PostgreSQL transactions.
-  Scalability – Read replicas for reporting.
